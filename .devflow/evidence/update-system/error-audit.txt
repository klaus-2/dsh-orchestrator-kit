FINDINGS — REQUIRES JUSTIFICATION
[RJ-1] MEDIUM — client.js:618 + client.js:610 — fetch REJECTION while status === 'restart'
  Pattern: the restart-preservation guard covers response-level failures only
  (`(!response.ok || info === null) && before.status === 'restart'`); a rejected
  fetch (bridge teardown/unload window) falls into the generic catch and sets
  status 'error'. From 'error', a later 404 never restores 'restart' (the guard
  requires before.status === 'restart'), so the "Restart the harness to finish"
  guidance is lost until a check succeeds. Host bridge behavior for an unloaded
  plugin route (404 vs rejection) is not verifiable from this repo. Trigger:
  install -> 'restart' -> 15 s auto-check fires while the route fetch rejects ->
  panel shows "Update check failed: ..." instead of the restart instruction.
  Smallest fix: in the catch, restore `before` when `before.status === 'restart'`,
  matching the documented intent ("a pending restart state stands").

[RJ-2] LOW — index.js:838 — 502 error body skips safeErrorText
  Pattern: response body uses String(error?.message ?? error); every other error
  response in this repo redacts via safeErrorText (index.js:614, 692, 695, 698,
  700, 719). safeErrorText is exactly that expression plus redactText
  (index.js:177-179), so the new route is the only one returning unredacted error
  text. Current error sources (authored constants, undici "fetch failed",
  JSON.parse fragments of the GitHub HTTPS response) carry no secrets or paths,
  so no provable leak today; it is a zero-cost convention deviation.

[RJ-3] LOW — client.js:633 — reply-level error code/diagnostic discarded
  Pattern: `reply?.error?.message ?? 'plugin manager did not answer'`. If the
  remote error object carries only { code, diagnostic } (the shape result.error
  uses at client.js:639-640), message is undefined and the user sees "plugin
  manager did not answer" although the manager answered with an error whose
  code/diagnostic are dropped. Remote reply shape is not verifiable from this
  repo. Smallest fix: append code/diagnostic to the thrown message.

[RJ-4] LOW-MEDIUM — client.js:739-741, 773 + 761 — primitives-less host leaves a dead "What's new" button
  Pattern: primitives degrade to undefined (frozen, plan C2: "no dialog"), and
  WhatsNewDialog returns null when primitives?.Modal is undefined — but the row
  renders its "What's new" button from `running` regardless of primitives. In a
  host without the base module, clicking it calls show() -> set(note) -> dialog
  renders null: a visible control with zero feedback. Degradation goes beyond
  the frozen "no dialog". Smallest fix: gate the row button on
  primitives?.Modal !== undefined.

[RJ-5] LOW — client.js:727 — SEEN_KEY read throw permanently drops the consumed record
  Pattern: load() removes WHATS_NEW_KEY before ask() (client.js:706) and keep()
  restores it on the Host-unanswered / older-copy paths (716, 718), but not on
  the record-consumed path: if window.localStorage.getItem(SEEN_KEY) throws at
  727 after the record was consumed (order === 0), load() returns and the record
  is gone without the dialog ever being shown. Storage worked at 706 in the same
  flow, so the window is nearly unreachable; consequence is silent permanent
  loss of one What's-new record.

[JE-1] index.js:563-568 — npm probe failure closes the `newer` gate (npmOk = false)
  Suppressed failure: any npm fetch error/timeout swallowed -> newer:false ->
  client shows "You have the latest version." (client.js:616) even though GitHub
  advertised a newer release. Justification: contract C1 frozen in the plan
  ("newer: npm.ok double-gate", plan line 36) and documented in the code comment
  (index.js:543-546): an unpublished release must never be advertised as
  installable. Caveat retained for the lead: during an npm outage (GitHub up,
  registry blocked — common behind proxies) the panel makes a false-success
  claim and the update is invisible until a manual re-check; the panel cannot
  distinguish "verified current" from "npm gate inconclusive".
